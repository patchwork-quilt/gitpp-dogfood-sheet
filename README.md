# gitpp-dogfood-sheet

**A lane sheet, stored as git.pp records and derived in CI by the public gitpp-action — the sheet is the state, and the fold is how you read it.**

This repository is a dogfood artefact from the SuperInstance lane-sheets line. It holds no code. Under `.gitpp/records/` are six git.pp provenance records that encode one complete agent workflow — the `sheet-reused` fixture from [SuperInstance/lane-sheets](https://github.com/SuperInstance/lane-sheets) (format `lanesheet 0.2`, titled *"The same inner sheet used by two outer cells: reuse is the plugin shape"*). On every push, the workflow in `.github/workflows/gitpp.yml` runs [patchwork-quilt/gitpp-action](https://github.com/patchwork-quilt/gitpp-action) over the records, and the derived state it prints *is* the workflow, reconstructed by rule from the records alone.

## The sheet these records encode

Three lanes. Two value cells hold texts (`input.a` = "the active ledger", `input.b` = "only the piping is public"). Two `sheet` cells, `use.first` and `use.second`, each pipe one text into the *same* inner sheet (`word-frame`) — one inner sheet, two invocation sites: reuse is the plugin shape. A prompt cell, `join.summary`, joins the two outputs with the template `A: {{first}} | B: {{second}}`. The sheet's declared output is `join.summary`.

## How the encoding works

Generated by `sheet_to_records.py` from the lane-sheets git.pp spike:

- One **genesis record** (`sheet-sheet-reused`) carries the sheet-level facts under `sheet.*` keys: `sheet.id`, `sheet.lanesheet`, `sheet.title`, `sheet.outputs`, and `sheet.lanes` — the lane structure, carried as data because lane membership is presentation, not derivation.
- One **record per cell** (`cell-<id>`) sets three declared keys: `cell.<id>.kind`, `cell.<id>.def` (the cell's payload), and `cell.<id>.inputs` (its port map).
- A cell record's **parents are its piping ancestry** — the records of the cells it pipes from, or the genesis record when it pipes from nothing. The record DAG is the dataflow DAG, so the fold's ancestry rules operate on the piping graph itself.

## What the Action's report should show (prediction, written before the first run)

- **6 records · 20 keys · 0 conflict(s) · 0 orphan(s).** Every key is set by exactly one record, so nothing is contested and nothing is orphaned: each cell's definition should appear in the derived state exactly as its record states it.
- The `sheet.*` keys should reconstruct the sheet's identity, format version, title, outputs, and the three-lane structure above.
- Each `cell.<id>.kind` / `.def` / `.inputs` triple should let a reader rebuild the workflow cell by cell — kinds `value`, `sheet`, `sheet`, `value`, `prompt`; `use.first` and `use.second` both naming the inner sheet `word-frame`, bound at port `text` from `input.a` and `input.b` respectively.
- The report should close with the fold's qualifications, verbatim: *"Mechanical resolution of labelled key conflicts only; the fold does not settle semantic conflicts. Digests authenticate content, not authorship. Arrival order is never an input."*

If the run disagrees with this prediction, the disagreement — not the prediction — is the finding, and it belongs in the open.
